# Capability-Based Security Model

## 1. Overview
ZERO OS Milestone 7.0.0 replaces ambient authority with an explicit, unforgeable capability token model. In traditional operating systems, a process executing with user authority can access any resource that the user has permission to touch. Under the ZERO OS Capability Model, a process possesses only those permissions explicitly conferred to it via opaque, kernel-managed capability handles.

## 2. Capability Handles & Structure
A capability handle (`cap_handle_t`) is a 32-bit random integer index into a kernel-isolated capability table (`CAP_MAX_ENTRIES = 256`).

Each capability record contains:
- `handle`: Unforgeable 32-bit identifier generated by kernel CSPRNG.
- `type`: Target resource category (`FILE`, `DIR`, `PROCESS`, `IPC`, `NET_SOCKET`, `DEVICE`, `SYSTEM`).
- `resource`: Canonical resource string (e.g. `/data/apps/calculator/config.cfg` or device ID).
- `perms`: Fine-grained bitmask (`CAP_PERM_READ`, `WRITE`, `EXEC`, `DELETE`, `ADMIN`).
- `pid`: Process identifier authorized to exercise the capability.
- `valid`: Active status flag.
- `revoked`: Explicit revocation tombstone flag.

## 3. Monotonic Attenuation
A process holding a capability may delegate authority to another process (such as a child worker) using `cap_duplicate_reduced()`. The model enforces strict monotonic attenuation:
$$\text{perms}_{\text{child}} \subseteq \text{perms}_{\text{parent}}$$
Any attempt to escalate privileges (e.g., requesting `CAP_PERM_WRITE` from a read-only parent handle) immediately causes `cap_duplicate_reduced()` to reject the request and return `CAP_INVALID_HANDLE`.

## 4. Immediate Revocation
Capabilities support instantaneous revocation via `cap_revoke()`. When revoked:
1. The kernel marks the handle's `revoked` flag.
2. Any subsequent invocation of `cap_validate()` returns `SEC_ERR_REVOKED`.
3. Associated open descriptors or buffers are closed and detached.
4. An `AUDIT_EVENT_CAP_REVOKE` event is appended to the audit ring buffer.

## 5. Kernel Verification API
- `cap_create(pid, type, resource, perms)`: Allocates and binds a new capability token.
- `cap_validate(handle, pid, type, req_perms)`: Verifies ownership, active status, and permission bitmask.
- `cap_check_resource(pid, type, resource, req_perms)`: Quickly audits whether a process has authority over a given path.
- `cap_enumerate_process(pid, out_caps, max_caps)`: Safely exports a process's capability list for user-space inspection (e.g., ZERO Security Center).
